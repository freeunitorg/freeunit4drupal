# Build freeunit4drupal beside DDEV, not against it

On the evidence available on 2026-10-07, yes, with conditions. The FreeUnit community should build freeunit4drupal as a narrow, Docker-free tool for Drupal developers on Linux and macOS. It should be one Go binary that runs one FreeUnit instance per user for all projects. It should ship its own matched PHP 8.3, 8.4 and 8.5 builds, serve each project at `<project>.localhost` with local TLS, use the host's MariaDB, MySQL or SQLite, capture mail with Mailpit, and read existing `.ddev/` configuration live. It should work beside DDEV, because **60% of Drupal survey respondents used DDEV in 2024, 93% of DDEV users recommended it in 2025, and drupal.org names it the recommended tool**. The gap is real but narrow. DDEV's reported failures come from layers it does not control (Docker providers, file sync, VPN certificate interception, hosts files). The only Drupal-specific tools without a container runtime are a trial launcher limited to SQLite and one site, and an alpha created on 2026-09-19. Laravel Herd supports Drupal on macOS and Windows, but it sells databases, mail capture and per-request Xdebug in a paid tier and has no Linux version. FreeUnit 1.37.0 already serves Drupal's request path, is built to run several PHP versions in one server, and isolates each project in its own processes. It has no macOS package, it cannot supervise databases, and **it fails every application request on Apple Silicon until a 1.37.1 tag ships the fix that merged on 2026-10-07**. Go ahead only if three conditions hold: about three weeks of experiments confirm the PHP build and isolation design, two maintainers commit to the work, and 1.37.1 is tagged before any macOS release. Windows users run the Linux build in WSL2, as DDEV's Windows users already do, until FreeUnit itself runs on Windows. The tool must be positioned on simplicity, no Docker, parity with FreeUnit in production and resource use once measured, never on speed.

## 1. DDEV holds Drupal, and its failures come from the Docker layers

DDEV is the default local tool for Drupal. drupal.org says "DDEV is the recommended local development tool for Drupal". The community reached that status through an ideas issue that was opened in April 2018 and closed in June 2024 ([Local server setup](https://www.drupal.org/docs/develop/local-server-setup); [project/ideas issue 2965681](https://git.drupalcode.org/project/ideas/-/work_items/2965681)). **In the Ironstar developer survey, DDEV use rose from 42% in 2023 to 60% in 2024. In 2025, 93% of DDEV users recommended it, against 51% for Lando** ([Ironstar 2024, archived](https://web.archive.org/web/20251122215514/https://www.ironstar.io/devsurvey24/); [Ironstar 2025, archived](https://web.archive.org/web/20260212040038/https://www.ironstar.io/devsurvey25/)). DDEV's opt-in telemetry counted **30,682 unique users in September 2026**. Drupal project types are 11,617 of 30,913 project-type entries, or 37.6% ([DDEV usage statistics](https://ddev.com/usage-stats/)). The same page warns that an Amplitude event quota makes the data "significantly incomplete", so every DDEV count in this report is a lower bound. Hosting companies support the default. Acquia's quickstart is built on DDEV, Upsun documents it, and Pantheon is the target of 51.7% of DDEV's bundled `ddev pull` runs ([Acquia local development](https://dev.acquia.com/cloud-platform/local-dev/); [Upsun: DDEV](https://developer.upsun.com/docs/development/local/ddev); [DDEV usage statistics](https://ddev.com/usage-stats/)).

DDEV is one Go binary that writes Docker Compose files. One Drupal site runs in at least four containers: a web container with nginx or Apache, php-fpm and Mailpit, a database container, a shared Traefik router and a shared ssh-agent ([How DDEV works](https://docs.ddev.com/en/stable/users/usage/architecture/)). A default project downloads **about 704 MiB of compressed images** before any per-project build (sum of the image sizes in research/ddev-incumbent.md section 7, from [Docker Hub](https://hub.docker.com/r/ddev/ddev-webserver/tags)). Medians of DDEV's nightly benchmark runs from 2026-08-31 to 2026-09-30, computed in research/ddev-incumbent.md section 7, are 12.2 s for `ddev start` with OrbStack and 21.0 s with Docker Desktop on Apple Silicon, both with Mutagen, and 30.0 s with Docker Desktop on traditional Windows. Each run starts with images already present, and each platform runs on different hardware ([DDEV performance history](https://ddev.github.io/ddev/perf/history.ndjson); [Docker Provider Performance](https://ddev.com/blog/docker-performance/)). These numbers describe DDEV only. Nobody has measured a native FreeUnit start against them, so this report makes no comparison.

The failures that users report sit where Docker meets the host. Docker Engine 28.0.0 broke DDEV's Mutagen file sync until a fix the next day. Issue 8054, "Docker 29 can't access or delete existing containers", has been open since 2026-01-23. macOS 15.7 caused freezes. Zscaler and GlobalProtect break TLS. Fritz!Box routers refuse DNS answers of 127.0.0.1. Hosts-file edits fail on Windows 11 ([issue 7015](https://github.com/ddev/ddev/issues/7015); [issue 8054](https://github.com/ddev/ddev/issues/8054); [issue 7678](https://github.com/ddev/ddev/issues/7678); [issue 7209](https://github.com/ddev/ddev/issues/7209); [DDEV networking](https://docs.ddev.com/en/stable/users/usage/networking/); [issue 8448](https://github.com/ddev/ddev/issues/8448)). About endpoint security software that made every port look busy, DDEV's lead maintainer wrote: "Changing DDEV for every harsh environment is a never-ending problem" ([issue 7921](https://github.com/ddev/ddev/issues/7921)). A native process removes the container VM, the file-sync layer and the Docker provider's release schedule. It does not remove trust stores, ports, DNS or VPN interception. It also adds a new duty, which section 3 describes: building and patching PHP for every platform.

Every DDEV mode on Windows needs WSL2. The recommended mode runs Docker CE inside a WSL2 distribution. "Traditional Windows" still needs Docker Desktop or Rancher Desktop, and both run on WSL2 ([DDEV installation: Windows](https://docs.ddev.com/en/stable/users/install/ddev-installation/#windows)). Docker Desktop is free only for organisations with fewer than 250 employees and less than USD 10 million in annual revenue. Paid seats cost USD 9 to 24 per user per month ([Docker Desktop licence](https://docs.docker.com/subscription/desktop-license/); [Docker pricing](https://www.docker.com/pricing/)). DDEV's Windows installer sets up the free Docker CE inside WSL2, and DDEV recommends Docker CE on Linux, so the licence question applies mainly to macOS teams in larger companies. There, **55.6% of DDEV's macOS users run Docker Desktop and 32.7% run OrbStack**, which costs USD 8 per user per month for business use ([DDEV usage statistics](https://ddev.com/usage-stats/); [OrbStack pricing](https://orbstack.dev/pricing)).

DDEV has many features and few people and little money. The DDEV Foundation, a US 501(c)(3) nonprofit, had USD 114,757 of income in 2025. Two paid maintainers write almost all the code. Monthly sponsorship is **USD 10,134, which is 84.4% of a USD 12,000 goal** ([ProPublica](https://projects.propublica.org/nonprofits/organizations/872477578); [sponsorship feed](https://ddev.github.io/sponsorship-data/data/all-sponsorships.json)). The maintainers call the outlook for discretionary funding "horrible" and name burnout and a maintainer in Ukraine as risks ([2026 plans](https://ddev.com/blog/2026-plans/)). DDEV's shipped and planned work extends the Docker base: rootless runtimes became stable in v1.25.3, shared image layers are planned in issue 8865, and cloud workspaces run on coder.ddev.com ([v1.25.3 notes](https://github.com/ddev/ddev/releases/tag/v1.25.3); [issue 8865](https://github.com/ddev/ddev/issues/8865)). None of it is a Docker-free runtime. The most-wanted feature, Apple's container framework, is being prototyped through a Docker-API shim ([issue 7372](https://github.com/ddev/ddev/issues/7372); [coder.ddev.com announcement](https://ddev.com/blog/coder-ddev-com-announcement/)). A new tool should not plan for DDEV to disappear, and it should not expect DDEV to build a native runtime in 2026.

The table sizes the segments from DDEV's seven-day environment chart (24,562 users on 2026-10-06, the sum of the chart's seven categories; 17 Codespaces users fit no row of the table), the only current breakdown by platform ([DDEV usage statistics](https://ddev.com/usage-stats/)). The chart covers all 27 DDEV project types, so the Drupal-only counts are smaller by an unknown factor (unverified). The Launcher row comes from a recount of release assets on 2026-10-07 ([cms-launcher releases](https://github.com/drupal/cms-launcher/releases)).

The macOS group is the largest and pays the most for Docker. The WSL2 group already accepts WSL2. Traditional Windows users and most Launcher users cannot be served until FreeUnit runs on Windows.

## 2. Docker-free rivals prove demand but leave the developer gap open

Laravel shows what a strong native tool can do, and what it cannot do. Laravel Herd bundles nginx, its own PHP builds, dnsmasq and local certificates behind one installer. At its 2023 launch it shipped "PHP (both CLI and FPM) as statically compiled binaries" built with static-php-cli ([Herd announcement, archived](https://web.archive.org/web/20231225135644/https://beyondco.de/blog/announcing-laravel-herd)). Laravel's install page moved from Docker and Sail first in 2022 to Herd and php.new, and a commit on 2025-02-25 deleted the Sail sections ([laravel/docs e82816b331](https://github.com/laravel/docs/commit/e82816b331)). In the State of Laravel survey, local non-container environments rose from 58.41% in 2023 to 64.42% in 2026. Virtualised setups fell from 14.73% in 2021 to 2.75% in 2026. Containers moved between 43.85% and 47.39% from 2022 to 2026 and stood at 46.38% in 2026, up from 37.46% in 2021 ([State of Laravel results](https://stateoflaravel.com/results)). Read together, these shares suggest that Herd took share from virtual machines and manual setups more than from Docker; the data are correlational (research/competitors-and-native-precedents.md section 3). Drupal is the counter-example: with no strong native option, about 70% of 829 Drupal survey respondents used containers in 2023 ([Ironstar 2023, archived](https://web.archive.org/web/20250909001037/https://www.ironstar.io/devsurvey23/)). Native tools won in Laravel when they were packaged well and endorsed by the framework's own documentation. Both surveys are self-selected, so treat the shares as directional.

Herd also shows the business model that works today. The core is free. Herd Pro sells services, mail capture, dump capture and per-request Xdebug for EUR 99 per year, or EUR 299 per year for ten licences ([herd.laravel.com](https://herd.laravel.com/)). On Windows, Herd needs an administrator install for its HerdHelper service, which edits the hosts file. It runs one `php-cgi.exe` per PHP version, because PHP has no FPM on Windows ([Herd for Windows installation](https://herd.laravel.com/docs/windows/getting-started/installation); [herd-community issue 1675](https://github.com/beyondcode/herd-community/issues/1675)). Windows 11 Smart App Control blocks its unsigned PHP extension DLLs ([herd-community issue 1757](https://github.com/beyondcode/herd-community/issues/1757)). The native Windows tools in this research share the same problems: host names, which need a privileged helper for the hosts file or a DNS proxy unless the tool uses a PAC proxy as Symfony CLI does; antivirus, Smart App Control and code signing; conflicts on ports 80 and 443; and supervision of php-cgi processes, because PHP has no FPM on Windows.

Besides Herd, three tools offer Drupal without Docker, and all three are young or limited. The **Drupal CMS Launcher** is maintained by the Drupal Association and community contributors. It runs a static PHP 8.4 with `php -S`, supports one site, uses SQLite only and has no HTTPS. Drupal's own documentation calls it "a trial tool" ([cms-launcher README](https://github.com/drupal/cms-launcher); [Drupal CMS launcher page](https://project.pages.drupalcode.org/drupal_cms/get-started/cms-launcher/)). Its last release was v1.0.9 on 2026-03-23. A recount of its release assets on 2026-10-07 gives **13,181 installer downloads: 8,500 for Windows (64.5%), 4,037 for macOS and 644 for Linux** ([cms-launcher releases](https://github.com/drupal/cms-launcher/releases)). **Drupack**, "Drupal as a single binary", is a GPL-2.0 alpha created on 2026-09-19. Its releases 1.0.0-alpha5 and 1.0.0-alpha6 came out on 2026-10-05 and 2026-10-07, it has 4 stars and one author, and its README mentions Caddy, SQLite, Drush and DDEV databases ([tresbientech/drupack](https://github.com/tresbientech/drupack)). The competitor research (research/competitors-and-native-precedents.md) does not cover Drupack, so its mechanisms are unverified. **lerd**, a "Herd-like" tool for Linux and macOS built on rootless Podman, reached 1,373 stars between 2026-03-17 and 2026-10-07. It writes Drupal's `settings.php`, and it added host PHP on macOS because of the bind-mount cost ([lerd-env/lerd](https://github.com/lerd-env/lerd)). No Drupal-specific tool serves the developer who needs MariaDB, HTTPS, several sites and Xdebug without any container runtime. Laravel Herd, which lists Drupal among its supported CMSs, does this on macOS and Windows, with the databases, mail capture and per-request Xdebug in its paid Pro tier, and it has no Linux version ([Herd supported frameworks](https://herd.laravel.com/docs/macos/extending-herd/supported-frameworks); [herd.laravel.com](https://herd.laravel.com/)).

The choice of server engine needs the strongest case for the alternatives. **FrankenPHP** is the closest existing server. It embeds PHP in a Go and Caddy binary, issues local certificates with Caddy's CA, exposes a JSON admin API and is maintained under the PHP Foundation. It **has run natively on Windows since v1.12.0 (2026-03-06)** ([php/frankenphp](https://github.com/php/frankenphp); [pull request 2119](https://github.com/php/frankenphp/pull/2119); [PHP Foundation](https://thephp.foundation/blog/2025/05/15/frankenphp/)). Its fully static musl builds cannot load Xdebug, and one binary carries one PHP version (an inference in research/competitors-and-native-precedents.md) ([FrankenPHP static builds](https://github.com/php/frankenphp/blob/main/docs/static.md)). Symfony CLI shows a lighter pattern: a Go front server over php-fpm or php-cgi, a CA derived from mkcert, and a PAC proxy instead of DNS ([symfony-cli](https://github.com/symfony-cli/symfony-cli)). If the only goal were a Docker-free Drupal tool, FrankenPHP, or php-fpm on Linux and macOS and php-cgi on Windows, would be shorter paths, and FrankenPHP already runs natively on Windows. The case for FreeUnit is different. FreeUnit is built to load several PHP versions into one server, gives each project its own processes, user and limits, and reconfigures live over one JSON API. That design matches "many projects, several PHP versions, one daemon". A cheaper route to parity also exists: a DDEV add-on that runs FreeUnit inside DDEV's web container, as DDEV's own FrankenPHP add-on does ([ddev-frankenphp](https://addons.ddev.com/addons/ddev/ddev-frankenphp)). It would serve the developers who already use DDEV and needs no PHP builds, no supervisor and no macOS packaging, but it keeps Docker. The research did not cost it; docs/plan.md keeps it as an optional track and as the fallback if the conditions fail. For the FreeUnit community, the tool is also the entry path to FreeUnit in production. That parity argument has an unknown audience today: FreeUnit's repository has 57 stars, drupal.org names no FreeUnit or NGINX Unit server, and the only FreeUnit image in Drupal's CI is a dev-branch image added by a FreeUnit maintainer (research/drupal-developer-requirements.md, testing section).

The history of local tools shows two ways to fail. Tools funded by one vendor ended when the vendor changed strategy: Acquia Dev Desktop on 2021-06-30 with about four months' notice, Bitnami's native installers by 2022-11-30, and Pantheon Localdev in June 2023 ([Acquia announcement, archived](https://web.archive.org/web/20220129114516/https://dev.acquia.com/blog/announcing-acquia-dev-desktop-end-life); [Bitnami](https://blog.bitnami.com/2022/11/focusing-on-cloud-native-solutions.html); [Pantheon](https://docs.pantheon.io/release-notes/2023/02/localdev)). Tools that depended on one or two people stalled or changed terms. Drupal VM is archived, Docksal's last release was on 2024-05-24, and Laragon has required a licence since version 7: commercial use is paid, and non-commercial use is free with reminder pop-ups ([drupal-vm](https://github.com/geerlingguy/drupal-vm); [docksal](https://github.com/docksal/docksal); [Laragon pricing](https://laragon.org/pricing)). Lando's sponsorship goal of USD 5,000 a month is 4% funded ([Lando sponsors](https://github.com/sponsors/lando)). freeunit4drupal therefore needs more than one maintainer from the start, and no single vendor should fund it.

## 3. FreeUnit 1.37 can serve Drupal; packaging and supervision are missing

The request path is ready. FreeUnit routes can reproduce Drupal's `.htaccess` protections. Its Drupal howto already translates them into a deny list, a list of PHP entry points and a `share` that falls back to `index.php` ([howto/drupal.rst](https://github.com/freeunitorg/docs/blob/8326bb78610/source/howto/drupal.rst)). FreeUnit discovers every `*.unit.so` module in its modules directory, and an application of type `php 8.4` picks its module by version prefix. Projects on different PHP versions should therefore be able to share one server, which experiment E2 in docs/plan.md tests with the tool's own builds ([nxt_application.c:1674-1724](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_application.c#L1674-L1724)). A per-project `php.ini` can be set with `options.file`. `PHP_INI_SCAN_DIR` also works, because FreeUnit sets the environment before PHP starts. TLS bundles are uploaded to `/certificates/<name>` and chosen by SNI, and since 1.37.0 they are replaced in place without a restart ([certificates.rst](https://github.com/freeunitorg/docs/blob/c5a372568cd3ebb7d4ed9ef13b23ef5d2584f028/source/certificates.rst#L63-L115)). Version 1.37.0 also added conditional requests and byte ranges for static files. It fixed the bug where a worker running Drupal's terminate phase was counted as idle ([CHANGES](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/CHANGES)). unitd runs as an ordinary user with every path on the command line, so several instances should be able to coexist (a code reading, not yet run).

Several defaults would hurt a developer if the tool left them alone. **An application without a `processes` object gets exactly one worker, started when the configuration is applied.** The code copies the default `processes` value of 1 into both `max_processes` and `spare_processes` in that case ([nxt_router.c:3209-3224](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_router.c#L3209-L3224)). A paused debugger then holds the only worker, and every other request to that project waits. Request bodies over 8 MiB get 413 until `max_body_size` is raised. `options.admin` is applied after `php_module_startup()`, so it cannot load a `zend_extension`, and by the same reading it cannot set `xdebug.mode` (not yet run; section 5) ([nxt_php_sapi.c:445-455](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_php_sapi.c#L445-L455); [nginx/unit issue 785](https://github.com/nginx/unit/issues/785)). Per-application `stdout` and `stderr` files are ignored in `--no-daemon` mode ([nxt_application.c:1601](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_application.c#L1601)). Error pages say only "Error 503.". There is no HTTP/2 yet; seven open pull requests for it target milestone 1.38, from stage 1 in [pull request 463](https://github.com/freeunitorg/freeunit/pull/463) to stage 4 in [pull request 479](https://github.com/freeunitorg/freeunit/pull/479). Route globs are case-sensitive. On a case-insensitive file system, which macOS uses by default (unverified in this research), a request for `/core/composer.JSON` passes the howto's deny list, as the howto itself warns. The howto still lists `core/authorize.php`, which Drupal 12 removed. It says nothing about uploads, forwarded headers, TLS or private files (research/drupal-developer-requirements.md, FreeUnit section).

FreeUnit supervises PHP workers and nothing else. An `external` application counts as started only after it calls `nxt_unit_init()` and sends libunit's READY message. `mariadbd` or Mailpit would never send it, and with the default `start_timeout` of 0, FreeUnit waits forever ([nxt_unit.c:698](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_unit.c#L698); [nxt_router.h:144](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_router.h#L144)). Drupal cron needs a timer until the "schedules" pull request merges. That pull request is open and says "This feature is for 1.38.0" ([pull request 452](https://github.com/freeunitorg/freeunit/pull/452)). The 1.38.0 tracking issue also plans a PHP worker mode, in which one PHP process keeps the application in memory between requests ([FreeUnit issue 596](https://github.com/freeunitorg/freeunit/issues/596)). A FreeUnit production server in worker mode would behave differently from a script-per-request development server, so a parity claim must name the mode (docs/plan.md section 7 item 20). Because FreeUnit supervises only PHP workers, the tool must run its own supervisor for unitd, databases, Mailpit and cron.

Installation is the largest gap. The 1.37.0 release attaches Debian 13 amd64 packages only. packages.freeunit.org serves build inputs, not packages. The Homebrew tap still builds NGINX Unit 1.34.2 ([1.37.0 release](https://github.com/freeunitorg/freeunit/releases/tag/1.37.0); [packages.freeunit.org](https://packages.freeunit.org/); [homebrew-unit](https://github.com/freeunitorg/homebrew-unit)). Homebrew's own `php` formula builds no embed SAPI, and FreeUnit's PHP module needs one ([php.rb](https://github.com/Homebrew/homebrew-core/blob/2b1c5d8ca5b8399a327fd0979db34e882ced81bf/Formula/p/php.rb#L162-L177)). The macOS CI job runs only the C test programs: "No modules, no pytest, no sudo" ([build-test-macos.yml:25-28](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/.github/workflows/build-test-macos.yml#L25-L28)). **FreeUnit 1.37.0 rejects every shared-memory segment on Apple Silicon, whose pages are 16 KiB.** The fix merged on 2026-10-07, and a `git ls-remote` on the same day found no 1.37.1 tag ([issue 595](https://github.com/freeunitorg/freeunit/issues/595); [pull request 598](https://github.com/freeunitorg/freeunit/pull/598)). A possible path exists. The released static-php-cli 2.8.5 builds a shared `libphp` on Linux and macOS. On Linux it does so only with a target that links libc dynamically, and the documented one is glibc (`native-native-gnu.2.17`); shared extensions, which Xdebug needs, have the same condition ([LinuxBuilder.php at 2.8.5](https://github.com/crazywhalecc/static-php-cli/blob/2.8.5/src/SPC/builder/linux/LinuxBuilder.php#L105-L118); [env.ini at 2.8.5](https://github.com/crazywhalecc/static-php-cli/blob/2.8.5/config/env.ini#L83-L90)). One build could then give the CLI, the embed library and the FreeUnit module the same PHP. No one has yet linked a FreeUnit module against that library, which is why it is the first experiment.

The performance evidence argues against a speed claim. For a public Yii3 benchmark of 2026-10-05, the FreeUnit maintainer estimates that about 85% of FreeUnit's CPU time per request is the framework's bootstrap and that FreeUnit's router and IPC take 5 to 6% ([FreeUnit issue 596](https://github.com/freeunitorg/freeunit/issues/596); [yii3-benchmarks](https://yii3-benchmarks.github.io/app-api/)). That is an estimate from one framework benchmark, not a measurement of Drupal. A Drupal one-shot cron with OPcache on but no `file_cache` ran 1.6 times slower than with OPcache off, which shows how easily a chosen baseline produces a result ([finding](https://github.com/andypost/freeunit-drupal/blob/master/docs/findings/opcache-shm-lives-in-prototype.md)). Memory per worker on a real Drupal site, MariaDB behaviour and runs on more than two cores are still unmeasured ([needs-measurement.md](https://github.com/andypost/freeunit-drupal/blob/master/docs/findings/needs-measurement.md)). Resource use against DDEV is also unmeasured. Removing the VM and about 704 MiB of images makes lower use likely, but that stays unverified until both tools run on one machine.

Only two FreeUnit changes block the plan. The 1.37.1 tag must ship the Apple Silicon fix. macOS CI must build and test the PHP module, so that the same break cannot reach a release again. Four more changes would remove workarounds that the tool otherwise carries. FreeUnit could apply `options.admin` before PHP starts (60 to 120 lines), honour per-application log files in foreground mode (3 to 10 lines), merge schedules, and give error pages an opt-in reason (150 to 300 lines). These sizes are judgement from reading the code (research/freeunit-capabilities.md section 11). Two more changes become blockers only if experiments fail: loading two PHP modules built against different `libphp` libraries in one server, and keeping one broken project from failing a reconfiguration for every project. Windows is a separate project. The companion freeunit-windows research, which is unpublished on 2026-10-07, so readers cannot check it yet, estimates 10,000 to 18,500 new lines of C plus 4,000 to 8,000 changed lines, and notes that NGINX Unit's maintainers refused a Windows port in 2021 ([nginx/unit issue 604](https://github.com/nginx/unit/issues/604)). One change must not happen. Renaming the PHP SAPI from "cli-server" would turn off OPcache on PHP 8.4 and older, because those versions start OPcache only for SAPI names on a fixed list ([php-src 3088d640684](https://github.com/php/php-src/commit/3088d640684)).

## 4. Build a Go supervisor around one FreeUnit instance per user

The tool itself does not embed PHP; FreeUnit does. So the tool needs no cgo, and Go fits. DDEV and Symfony CLI both build with cgo off and cross-compile with goreleaser, and the reusable code for the hard parts is written in Go ([DDEV Makefile](https://github.com/ddev/ddev/blob/598e255e233f060dd371a9abc46c73742695f9b4/Makefile#L30); [Symfony CLI .goreleaser.yml](https://github.com/symfony-cli/symfony-cli/blob/a9011678fe13f2d6778768a09a01c94ac8e519e9/.goreleaser.yml#L17)). Line counts taken for this report at the commits the research cites give the scale. mkcert, which holds the CA and trust-store code, is 1,381 lines under a BSD-style licence, of which the CA and trust-store files are 988. DDEV's hosts-file helper is 308 lines under Apache-2.0. Symfony CLI, the closest comparable tool, is 23,066 lines (lines in non-test `.go` files, comments included) ([mkcert](https://github.com/FiloSottile/mkcert/tree/1c1dc4ed27ed5936046b6398d39cab4d657a2d8e); [ddev-hostname](https://github.com/ddev/ddev/tree/598e255e233f060dd371a9abc46c73742695f9b4/cmd/ddev-hostname); [Symfony CLI](https://github.com/symfony-cli/symfony-cli/tree/a9011678fe13f2d6778768a09a01c94ac8e519e9)). Symfony CLI is AGPL-3.0, so the tool may copy its ideas but not its code. FreeUnit's Rust `unitctl` offers little to reuse: its OpenAPI client is generated at build time with Java, and it ships no Windows binary ([unitctl 1.37.0](https://github.com/freeunitorg/freeunit/releases/tag/unitctl%2F1.37.0)). A PHP phar cannot install the PHP it runs on.

One FreeUnit instance per user should serve every project, routed by the `Host` header. This matches DDEV's shared router and keeps one certificate list for SNI. Each project gets its own application, its own prototype process and its own OPcache. The default name is `<project>.localhost`. RFC 6761 reserves these names for loopback. Chromium and Firefox 84 and later resolve every `*.localhost` name without DNS, curl does so since 7.85.0, systemd-resolved synthesises the answer ([systemd-resolved.service.xml](https://github.com/systemd/systemd/blob/a31540ec8272da2ba9a98c98629917d12ad77c78/man/systemd-resolved.service.xml#L111-L113)), and browsers treat the names as secure contexts over plain HTTP ([RFC 6761](https://www.rfc-editor.org/rfc/rfc6761#section-6.3); [Chromium url_util.cc](https://github.com/chromium/chromium/blob/f24386a5821b5ba5fc100599fe1ad7f4969158f0/net/base/url_util.cc#L582-L589); [Mozilla bug 1220810](https://bugzilla.mozilla.org/show_bug.cgi?id=1220810); [curl 7.85.0](https://curl.se/ch/7.85.0.html); [MDN: secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)). These names need no hosts file, no sudo and no network, so offline work, VPNs and DNS-rebinding filters do not break them. Drupal scopes its session cookie to `.example.localhost` for such a name ([SessionConfiguration.php](https://github.com/drupal/drupal/blob/89f3e765bb2ef1620ca89302ce8ee6d7ab263332/core/lib/Drupal/Core/Session/SessionConfiguration.php#L128-L147)). The exception is Safari on macOS 15 and older, which needs an opt-in hosts entry. A WebKit bug reporter confirms that macOS 26 resolves these names ([WebKit bug 160504](https://bugs.webkit.org/show_bug.cgi?id=160504)). Imported DDEV projects keep their `<name>.ddev.site` names, which public DNS resolves to 127.0.0.1.

The notes disagree on ports, and the default that needs no privilege should win. On macOS a non-root process can bind ports below 1024 only on the wildcard address. The XNU kernel checks the reserved-port privilege only when the address is not 0.0.0.0 or `::`, so `127.0.0.1:443` fails and `*:443` works ([in_pcb.c](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/netinet/in_pcb.c#L989-L1000)). A wildcard listener exposes the port to the local network. The architecture note pairs it with a first route step that returns 403 to any source outside loopback, but the TCP port and the TLS handshake stay reachable from other machines (docs/plan.md experiment E6 tests the guard). On Linux, `setcap cap_net_bind_service` on unitd works, and FreeUnit 1.37.0 keeps the capability in its main process only. But the capability puts unitd in secure-execution mode, makes it non-dumpable, and must be applied again after every update ([nxt_capability.c](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_capability.c#L6-L21); [ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)). The default should therefore be high ports on 127.0.0.1, with ports 80 and 443 as an explicit opt-in. A running DDEV holds 80, 443, 8025 and 8026 through its router, so the tool's defaults, including the Mailpit web UI, avoid all four (research/ddev-incumbent.md section 2).

HTTPS should be on by default once the user trusts a local CA. Drupal names the session cookie `SESS` over HTTP and `SSESS` over HTTPS, and it sets the `Secure` flag only over HTTPS. Google requires HTTPS redirect URIs except for localhost, and whether it treats `<name>.localhost` as localhost is unverified ([Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)). The tool should create its own CA with code derived from mkcert, or reuse a trusted mkcert CA, which most DDEV users already have. It should issue one leaf per project for `<name>.localhost` and `*.<name>.localhost`, because many browsers reject a second-level wildcard such as `*.localhost` ([mkcert cert.go](https://github.com/FiloSottile/mkcert/blob/1c1dc4ed27ed5936046b6398d39cab4d657a2d8e/cert.go#L148-L161)). Leaves should last 396 days and renew automatically. Apple limits TLS server certificates to 825 days ([Apple 103769](https://support.apple.com/en-us/103769)), and mkcert's source notes that macOS applies this limit "to all certificates, including custom roots" ([mkcert cert.go](https://github.com/FiloSottile/mkcert/blob/1c1dc4ed27ed5936046b6398d39cab4d657a2d8e/cert.go#L59-L61)), while the 398-day limits of Apple and Chrome exempt locally added roots ([Apple 102028](https://support.apple.com/en-us/102028); [Chromium certificate lifetimes](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/certificate_lifetimes.md)). Trusting the CA needs one elevation per machine. Firefox keeps its own NSS store, so the CA must also be imported with `certutil`: this is verified on Linux, DDEV reports the same need on Windows, and macOS is unverified.

PHP is the hardest part, because one build must serve three roles. Drush and Composer run on the CLI. FreeUnit runs the embed library. Drupal itself starts PHP from web requests. Package Manager finds a Composer executable through its own finder (the project's `composer/composer` package, then the `package_manager_composer_path` setting, then the `PATH`), and the Drupal CMS installer runs Composer through Symfony's `PhpExecutableFinder` ([ComposerExecutor.php](https://git.drupalcode.org/project/drupal_cms/-/blob/2.x/drupal_cms_installer/src/ComposerExecutor.php)). Under FreeUnit the `PHP_BINARY` constant should be empty, because the SAPI sets no executable location (a code reading; plan experiment E7 tests it). The finder checks a `PHP_BINARY` environment variable first, so the tool can set it in each application ([nxt_php_sapi.c:337](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_php_sapi.c#L337); [PhpExecutableFinder.php](https://github.com/symfony/process/blob/v8.1.7/PhpExecutableFinder.php)). The tool should ship one matched set per PHP minor version, OS and CPU, built in one static-php-cli run: the `php` CLI, a shared `libphp`, a `php8.x.unit.so` module built against it, and `xdebug.so`. The extension list follows Drupal core's 14 required extensions, plus OPcache, APCu, intl, mbstring, xmlwriter, the PDO drivers, zip, curl, OpenSSL, sodium and, for the CLI, pcntl. Drupal 12 also needs argon2 for password hashing ([PHP requirements](https://www.drupal.org/docs/getting-started/system-requirements/php-requirements)). PHP 8.3, 8.4 and 8.5 cover Drupal 10.4 and later, 11 and 12. PHP 8.3 is the version most often set in DDEV projects, at 34.5% ([DDEV usage statistics](https://ddev.com/usage-stats/)). Owning these builds means owning PHP's patch releases, which research/tool-architecture-options.md section 6 puts at about one a month, and shipping each security fix within days.

Databases and mail stay outside FreeUnit, under the tool's own supervisor. In DDEV's data, 63.4% of project database settings are MariaDB, 30.3% MySQL and 6.3% PostgreSQL ([DDEV usage statistics](https://ddev.com/usage-stats/)). MariaDB 11.8 publishes Linux x86_64 and Windows binaries, but no macOS binary and no Linux aarch64 binary ([MariaDB 11.8 release files](https://downloads.mariadb.org/rest-api/mariadb/11.8/latest/)). The first release should therefore use a MariaDB or MySQL server that the developer already has, from Homebrew or the distribution, and give each project its own data directory, port and socket. SQLite suits evaluators and needs no service, provided the shipped PHP links SQLite 3.45 or newer. Drupal has a documented history of "database is locked" errors under concurrent writes, so SQLite projects should get fewer workers until a measurement says otherwise ([drupal.org/i/1120020](https://www.drupal.org/i/1120020)). Mailpit ships as one binary for every platform and replaces DDEV's built-in mail capture ([Mailpit releases](https://github.com/axllent/mailpit/releases)). The supervisor runs `drush cron` on a timer until FreeUnit schedules ship. PostgreSQL, Redis or Valkey, and Solr come after the first release.

Drupal integration should follow DDEV's model with two changes. In native mode the tool writes its own `settings.freeunit4drupal.php`. `settings.php` includes it behind the tool's own environment variable, and it lists exact `trusted_host_patterns` instead of DDEV's `['.*']`. In DDEV mode, when a project has `.ddev/config.yaml` and no native file, the tool reads DDEV's configuration live with DDEV's merge rules. It sets `IS_DDEV_PROJECT=true` and regenerates `settings.ddev.php` only while that file still carries DDEV's `#ddev-generated` signature. The project's committed `settings.php` includes that file only when the variable is set ([drupal.go:73-95](https://github.com/ddev/ddev/blob/598e255e233/pkg/ddevapp/drupal.go#L73-L95)). The Drupal CMS Launcher already sets `IS_DDEV_PROJECT` itself to silence a warning ([Launcher settings.local.php](https://github.com/drupal/cms-launcher/blob/c5c55584383/settings.local.php)). Routes should come from the `drupal.json` file of the DrupalCI FreeUnit image. That file already denies private and temporary directories and serves compressed aggregates. The tool adds case-insensitive regular expressions and picks entry points per Drupal major. It takes only the routes. The same file disables `fastcgi_finish_request`, runs as `www-data` and allows 64 workers. The tool runs as the developer, keeps `fastcgi_finish_request` enabled because 1.37.0 counts detached workers as busy, and disables it only in a CI mode that matches DrupalCI ([drupal.json](https://gitlab.com/drupal-infrastructure/drupalci/drupalci-environments/-/blob/dev/php/8.5-ubuntu-unit/conf/unit/drupal.json)).

Xdebug should run in a second application per project, a pattern published for NGINX Unit in [nginx/unit issue 969](https://github.com/nginx/unit/issues/969). Xdebug reads its mode once, when its module starts ([xdebug.c](https://github.com/xdebug/xdebug/blob/64007df3a0925808022fb87b6c6f06febf058ee2/xdebug.c#L508)). So the twin application loads Xdebug through its own `php.ini` and the `XDEBUG_MODE` environment variable. A route sends requests to it while debugging is on, or only when an `XDEBUG_SESSION` cookie or argument is present. Requests without a trigger never load Xdebug, and switching is a route change. research/tool-architecture-options.md section 9 proposes instead to swap the project's `php.ini` and restart that one application; the twin avoids the restart and keeps the OPcache of the normal workers, at the cost of a second prototype process. Herd sells the same per-request behaviour in its paid tier. The command set should reuse DDEV's verbs where they make sense on the host: `start`, `stop`, `describe`, `launch`, `drush`, `composer`, `import-db`, `snapshot`, `xdebug` and `share`. DDEV hooks and host commands should run on the host. A CI mode should need no CA and no prompts and serve HTTP only. Telemetry should stay off. DDEV's own Amplitude use is about 45 million events a month against a free quota of 2 million ([issue 8614](https://github.com/ddev/ddev/issues/8614)).

## 5. Sequence the work behind experiments and the 1.37.1 tag

Six questions can still change the design, and each has a short experiment (research/freeunit-capabilities.md section 13; research/tool-architecture-options.md section 12). Can a FreeUnit module load a static-php-cli shared `libphp` with Xdebug, also when unitd carries a file capability? Do two such modules for different PHP minor versions load in one server, given that FreeUnit opens modules with `RTLD_GLOBAL`? Does one project whose PHP cannot start block reconfiguration for every other project? Does `XDEBUG_MODE` in an application's environment turn Xdebug on, while `options.admin` does not? Does Package Manager install a module from a web request when `PHP_BINARY` points at the CLI? Can a DDEV MariaDB snapshot be restored into a native MariaDB? A failure in the first three questions has a fallback: distribution PHP packages on Linux; on macOS, a static `libphp` linked into the module with `--lib-static` (docs/plan.md D6, unverified) or a Homebrew formula that builds the embed SAPI, which the FreeUnit tap already carries as `php-embed` at PHP 8.4.2; one unitd per PHP version; or a per-project validation before a shared reconfiguration. docs/plan.md lists every experiment with its steps and expected result. They fit in about three weeks, ending on 2026-10-30.

Linux comes first, because FreeUnit already works there and it is the build platform. macOS follows the 1.37.1 tag. Drupal 12.0.0 is planned for the week of 2026-12-07, the same week Drupal 10 reaches end of life on 2026-12-09, and Drupal 12 requires PHP 8.5 ([release schedule](https://www.drupal.org/about/core/policies/core-release-cycles/schedule); [Drupal 12 platform requirements](https://www.drupal.org/about/core/blog/announcing-drupal-1200-platform-requirements)). A Linux alpha that serves Drupal 12 in December 2026 is therefore the first useful target. A beta with macOS, databases, TLS and DDEV import fits before DrupalCon Orlando (2027-03-22 to 2027-03-25), where a BoF session can present it. DrupalCon Edinburgh (2027-10-25 to 2027-10-28) suits a 1.0 release ([events.drupal.org](https://events.drupal.org/)).

Windows depends on FreeUnit, not on the tool. About a quarter of DDEV's users run Windows, and 85% of them already work inside WSL2 ([DDEV usage statistics](https://ddev.com/usage-stats/)). The Linux build inside WSL2 serves them, with the same placement rule that DDEV gives: keep the project in the WSL2 file system ([DDEV FAQ](https://github.com/ddev/ddev/blob/3af9704770e/docs/content/users/usage/faq.md)). A native build depends on the companion freeunit-windows project, whose research is unpublished on 2026-10-07. FreeUnit has never run on Windows. A staged port needs a platform layer, a WSAPoll engine for bring-up, and then an engine based on ProcessSocketNotifications, which needs Windows 11 or Server 2022 or later. The PHP module can link the official windows.php.net builds only with an MSVC-compatible compiler such as clang-cl, and the first target is a foreground console process on x64. The Launcher's numbers show what waits on that work: 64.5% of its installer downloads are for Windows, and those evaluators are unlikely to install WSL2 (unverified). FrankenPHP already runs natively there, with gaps: no static or embedded builds, an archive that wraps the official php.net binary, `max_execution_time` always 0 ([FrankenPHP issue 2474](https://github.com/php/frankenphp/issues/2474)) and no service integration ([FrankenPHP issue 2442](https://github.com/php/frankenphp/issues/2442)).

The first public release is a medium-size Go program plus a build pipeline. Judged against Symfony CLI's 23,066 lines for a broader scope, the tool needs about 11,500 to 20,000 lines of Go, or about 26 to 42 person-weeks of work (judgement; no prototype exists). The pipeline that builds PHP 8.3 to 8.5, Xdebug and unitd for Linux x86_64, Linux arm64 and macOS arm64 is the long-term cost. research/tool-architecture-options.md section 10 counts about 10 artifacts per PHP minor version, rebuilt for every PHP patch release and every FreeUnit release. FreeUnit shipped 8 releases between April and October 2026 ([FreeUnit releases](https://github.com/freeunitorg/freeunit/releases)). DDEV, with two paid maintainers and USD 114,757 of income in 2025, shows the scale of effort that a sustained local tool needs. The stalled tools show what happens with one maintainer.

Adoption runs through Drupal's documentation. The official Local Development Guide asks anyone who wants another tool listed to open an issue in the Official Docs queue. The community "Local server setup" guide has child pages for tools and platforms. The Launcher's README lists alternatives and already names Laravel Herd as the choice without Docker ([Local Development Guide](https://www.drupal.org/docs/official_docs/local-development-guide); [Local server setup](https://www.drupal.org/docs/develop/local-server-setup); [cms-launcher README](https://github.com/drupal/cms-launcher)). DDEV needed six years to become the recommendation, so a listing among the alternatives is the realistic first goal. Releases should follow DDEV and Symfony CLI: GitHub Releases with checksums and signatures, an install script, a Homebrew tap formula, and notarized macOS binaries through the Apple Developer Program at USD 99 a year ([Apple Developer Program](https://developer.apple.com/programs/)).

## Conclusion

The decisive commitment is not the Go code. freeunit4drupal would become a distributor of PHP and FreeUnit binaries for three platforms, with the duty to ship every PHP security release within days. Herd funds that duty through a paid tier, and DDEV moves it into container images that its two paid maintainers rebuild for every release. A FreeUnit community project has neither yet, so it must settle its maintainers and funding before the beta, not after. If it cannot, a DDEV add-on that runs FreeUnit is the cheaper way to give Drupal developers FreeUnit parity, although it keeps Docker. The same build pipeline is also the most useful thing the project can give back to FreeUnit: tested macOS builds, a PHP module linked against a portable `libphp`, and one Drupal route template that the DrupalCI image, the FreeUnit dev kit and the local tool share.

The evidence also changes what success means. Displacing DDEV's 30,682 monthly users is the wrong target. The right targets are measurable: FreeUnit-based Drupal development without Docker on the two platforms where FreeUnit runs, an import of DDEV projects that works without edits, and a listing in Drupal's documentation. The largest signal of demand for Docker-free Drupal, the Launcher's Windows installer downloads (an upper bound on people, because auto-updates count), comes from the one platform FreeUnit cannot reach yet. That makes the native Windows port the dependency that decides whether the tool can grow beyond developers who already use DDEV.
